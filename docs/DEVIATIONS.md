# Design and execution log

- Initial pilot: 12 excluded trials, 512 messages, C=1 or 16, all six profiles. Completed with exact counts, no duplicates and no pending acknowledgments. Main series had not begun.
- Before main collection: added receive-request timestamps to support a check of the finite-window concurrency bound. Increased main backlog from 4096 to 16384 messages because the pilot showed high-concurrency trials would otherwise be very brief. Retained the fixed-backlog interpretation.
- Before main collection: replaced the primary RQ3 fixed-count prefill comparison with an independent 5-second publication series, ten randomized complete blocks, 16 publishers. This spans several nominal 1-second synchronization intervals; the original prefill remains raw supporting data. The one-publisher, 1024-message sensitivity series remains ten blocks. Neither is an open-loop SLA experiment or a long-duration soak.
- Infrastructure: the driver pod initially remained Pending due to the existing control-plane taint on homelab-02. Added a toleration only to that experiment pod. No node taints or unrelated resources were changed. Initial copy attempt before the driver existed failed; no experiment ran on a different environment.

- Main collection paused after 51 completed trials. Attempt Tmain052 returned a five-second client deadline during `AddStream`, before the publication/drain measurement began. NATS logged `$JS.API.STREAM.CREATE.Tmain052` taking 8.0186 seconds at 2026-09-23T21:42:30Z. The server reported no pod restart or cgroup OOM event; the underlying cause is not established. The original summary, panic log and broker log are retained. This is a setup-availability observation, not evidence of message loss or a measured publication-latency sample.
- Added append-only checkpoint/resume handling and stage-qualified create errors. No timed-path logic, timeout, workload size, configuration or repetition count changed. The first 51 complete trials remain; the failed setup is retained and its condition is retried under a fresh stream name before continuing the original deterministic order. Source version before the change is retained under data/environment/harness-v1. Tables estimate the performance of successfully initialized trials and do not include stream-creation availability.

- A second interruption followed completed trial Tmain088. The subsequent Redis-always C=1 256-message warm-up returned through an error path, and its deferred DEL cleanup raised a five-second socket timeout, masking the primary error. No timed Tmain089 measurement was collected. The complete original stack/log is retained as main-resume-v2.log. It is a warm-up/cleanup incident with an unknown primary operation, not classified as a successfully measured drain or proof of message loss.
- Administrative (create/inventory/delete) connection request budgets were extended from five to thirty seconds after these incidents. Redis publication and acknowledgment use five-second default socket read and write timeouts, not a whole-call deadline. Positive blocking XREADGROUP calls override the socket read timeout to BLOCK + 10 seconds: 10.1 seconds for ordinary 100 ms reads and 15 seconds for the victim’s five-second read. NATS publication and acknowledgment use five-second response waits; Fetch uses its explicit 100 ms or five-second client wait. The measured settings were unchanged; workload, timed code, policies, seed and complete-trial counts are unchanged. The fixed-count trial cleanup now logs a cleanup error without masking its primary error; the timed-publication and recovery cleanup paths retain their original panic-on-delete-error behavior. This change applies only outside the measured intervals, and its source is retained alongside v1 and v2. The original incident remains reported; completed measurements are preserved.

- Source/method clarification: the prospective phrase "synchronization requested on each operation" is interpreted in the manuscript as a configured synchronous append policy, not a hardware fsync for every message or synchronous JetStream consumer-state write. "Bounded steady-state path" is narrowed to a bounded append workload; stationarity is not assumed.

- A final environment audit recorded `/data` mount options from an experiment broker. Btrfs has `compress=zstd:3` enabled; each 512-byte payload consists of an eight-byte ID and repeated `x` bytes. The manuscript now explicitly records this compressibility and filesystem setting, without asserting measured per-file compression ratios. No workload or mount option was changed. The receipt is `data/environment/broker-mounts.txt`.

NATS-always also logged approximately 4.9925 seconds in deletion/read-loop processing for D022warm at 2026-09-23T22:48:50Z. The underlying cause is unestablished; subsequent storage-status checks showed available space, Redis AOF write status OK, and no cgroup OOM event on the inspected broker.
