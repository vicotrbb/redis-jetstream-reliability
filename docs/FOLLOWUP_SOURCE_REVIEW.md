## 2. Recovery-policy changes

### Redis

The current command specification dates `XREADGROUP CLAIM` to **8.4.0**. It leaves plain `XREADGROUP ... STREAMS key >` available and adds an explicit reclamation option. Thus the historical non-reclamation argument remains applicable to the plain new-message-read policy, but it is not a statement that all current Redis read policies require a separate reclamation loop. [Pinned command history](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/commands/xreadgroup.json#L10-L18).

In 8.10.2, the CLAIM path examines the pending list in delivery-time order, accepts idle age at least the requested threshold, transfers ownership, and updates delivery metadata. Pending eligible entries precede new entries. A blocked CLAIM read registers the next eligibility time; the server subsequently signals the stream when that time has passed. This removes the need for an application-issued `XAUTOCLAIM` poll in this policy, but it does not establish an exact wall-clock recovery bound. Sources: [claim processing](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L2082-L2167), [eligibility registration](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L3173-L3185), and [wake-up processing](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L5898-L5989).

The CLAIM response has **four elements per message**: ID, field-value data, prior idle time, and prior delivery count. The historical go-redis v9.7.0 decoder requires exactly two elements. A raw command and explicit response parser, or a separately validated newer client, is therefore required for this additional arm. Merely appending CLAIM arguments to the existing typed result path is insufficient. [Redis response specification](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/commands/xreadgroup.json#L134-L170), [old client decoder](https://github.com/redis/go-redis/blob/ed37c33a9037483ad2a6b1042e5eb6df89009a1c/command.go#L1545-L1555).

The existing `XAUTOCLAIM key group consumer min-idle-time start COUNT count` command also remains available in 8.10.2. A common-policy arm can retain it, while a separate CLAIM arm measures the new policy. These comparisons answer different questions: version sensitivity under a retained API, and recovery-policy sensitivity on a current server. [Pinned XAUTOCLAIM implementation](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L4762-L4799).

#### Scheduling check after the first primary deployment

The first deployment's larger CLAIM receipt excess prompted a source check, without changing the frozen collection procedure. The actual command, `XREADGROUP GROUP workers survivor COUNT 1 BLOCK 100 CLAIM <delta-ms> STREAMS <key> >`, follows the pinned parser and uses the required four-field reply decoder. The eligibility registration updates a watched timestamp, rather than creating a dedicated event-loop timer. During `blockedBeforeSleep`, ordinary blocking timeouts are handled first, eligible stream entries second, and ready keys thereafter. Sources: [argument parsing](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L2795-L2869), [watch registration](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L5923-L5940), [eligibility scan](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/t_stream.c#L5955-L5989), and [blocked-client processing](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/blocked.c#L825-L852).

The default cron frequency is 10 Hz; `serverCron` returns `1000/server.hz` milliseconds, and dynamic adjustment depends on connected-client count. The event loop polls until the nearest registered timer or an earlier socket event. This makes a roughly 100 ms quiet-loop wake-up interval a plausible scheduling contributor. It is neither a mandatory period nor a bound on all recovery overhead, and it does not imply a uniform delay distribution or an expected 50 ms delay. Sources: [default frequency](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/server.h#L119-L123), [dynamic adjustment](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/server.c#L1572-L1585), [cron return interval](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/server.c#L1855-L1859), and [poll scheduling](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/ae.c#L382-L403).

Both ordinary blocking timeout and watched eligibility checks use a strict past-time comparison. The scan budget covers all 16 default databases in one invocation, so repeated rounds over databases are not a supported explanation for this configuration. Shortening BLOCK would alter null-return and client-reissuance behavior, but would not itself create a dedicated eligibility timer. The raw old-client command retains its five-second socket timeout. Internal event timestamps were not instrumented; the paper presents source compatibility rather than a measured causal decomposition. Source files were independently retrieved and hashed in `revisions/20260924-followup/redis-scheduling-source-check.json`; third-party source copies are not part of the release.

### JetStream

The current implementation still adds a nominal one-millisecond delay to its pending-check timer and compares pending age with the acknowledgment deadline before adding an entry to the redelivery queue. These selected mechanisms agree with the historical source description; they do not establish that every scheduling detail is unchanged. [Current timer](https://github.com/nats-io/nats-server/blob/eb763679aa3c24a40dcd3012aa046ad1996d851c/server/consumer.go#L3363-L3373), [current expiry path](https://github.com/nats-io/nats-server/blob/eb763679aa3c24a40dcd3012aa046ad1996d851c/server/consumer.go#L6116-L6194), [historical expiry path](https://github.com/nats-io/nats-server/blob/1d6f7eaf0bd966dd02c95b8d5f624868f1a62544/server/consumer.go#L4608-L4723).

The server distinguishes timeout eligibility from subsequent delivery. The same configured `AckWait`, active pull demand, and explicit acknowledgment policy should be retained when evaluating version sensitivity. Neither a pending-entry timeout nor a received redelivery proves that the server detected process death. A live but non-acknowledging control can discriminate timeout behavior from any additional effect of killing the original consumer. This is a proposed experimental control, not a new measured finding.

## 4. Synchronization hypotheses and diagnostic traces

Redis documents grouping commands from multiple clients or a pipeline into a write and synchronization operation before returning replies. That is a plausible mechanism for concurrency-dependent acknowledgment cost. It is not evidence of the batch sizes or synchronization frequencies in this study. [Official persistence explanation](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/#how-durable-is-the-append-only-file).

On Linux, the current Redis source maps `redis_fsync` to **`fdatasync`**. Its always-mode AOF path checks failure and exits. NATS uses Go file `Sync()` in the inspected message-block path. A diagnostic trace must cover **both `fsync` and `fdatasync`**, across broker threads; an fsync-only trace would omit Redis's central Linux call. Sources: [Redis syscall mapping](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/config.h#L139-L146), [Redis AOF call](https://github.com/redis/redis/blob/498ecd0d6d007db11ddb3aea9428552598a78622/src/aof.c#L1581-L1598), and [NATS message-block synchronization](https://github.com/nats-io/nats-server/blob/eb763679aa3c24a40dcd3012aa046ad1996d851c/server/filestore.go#L8773-L8787).

For consumer-state diagnostics, also consider open flags and write calls: synchronous file-open flags can impose synchronization without a separate fsync call. Retain file identities, call durations, errors, traced thread IDs, and the timed-phase boundaries. Compare diagnostic runs with otherwise matched uninstrumented runs. Tracing perturbs execution; a syscall count is not an isolated causal estimate of the observed throughput difference. Nor does a successfully returned syscall constitute an experimental storage-fault test. The [Linux synchronization reference](https://man7.org/linux/man-pages/man2/fsync.2.html) also distinguishes data synchronization from directory-entry persistence.

## 5. Btrfs compression sensitivity

The official Btrfs documentation supports an inode-level intervention without changing host mount settings. `btrfs property set <fresh-directory> compression none` disables compression and is equivalent to `chattr +m`. The documented `no`/`none` property behavior requires btrfs-progs 5.18 or later and Linux 5.14 or later. [Property reference](https://btrfs.readthedocs.io/en/latest/btrfs-property.html).

The `m` attribute overrides compression mount options, and new files created beneath a directory inherit it. The separate `C` attribute disables copy-on-write. Do not substitute `chattr +C` for a compression-only intervention: that changes another storage mechanism. The `c` and `m` flags are mutually exclusive. [Btrfs inode attributes](https://btrfs.readthedocs.io/en/latest/ch-file-attributes.html).

Changing compression settings affects future writes, not existing extents. Compression is also subject to data compressibility and file-allocation behavior, including the documented fallocate exception. An enabled mount option alone does not prove that every broker extent was compressed. [Btrfs compression documentation](https://btrfs.readthedocs.io/en/latest/Compression.html).

A suitable proposed sensitivity procedure is to create dedicated, empty trial directories on the confirmed Btrfs-backed volume, establish the assigned compression policy before the broker creates files, and retain the mount options, property/attribute outputs, kernel and btrfs-progs versions, and attributes of actual broker-created descendants. Verify that the storage path is not a memory-backed emptyDir. Use the existing mount policy as one arm and explicit no-compression as the other; describe these as **compression-policy** treatments unless actual extent compression is measured. Do not remount the shared host filesystem or retroactively transform historical data. The feasibility and successful application of this procedure must be demonstrated on the homelab.

Fresh broker processes and empty directories remove the documented cross-trial accumulation of the broker's previous AOF or stream store. They do not reset shared-device allocation, filesystem metadata, caches, thermal state, or ambient load. Repeated reset campaigns on one host should not be described as independent hosts or as providing verified hardware-general interval coverage. These are design implications, not additional findings from the original data.

## 7. Claims supported after this review

The source-supported contribution is a reproducible comparison of specified recovery policies and acknowledgment costs under documented conditions. The follow-up can strengthen attribution by matching workloads, resetting broker-owned storage before trials, observing the actual timed phases, and including current releases. Which hypotheses survive those interventions must be decided from the resulting evidence. Source inspection cannot establish measured synchronization counts, a dominant Btrfs effect, general broker superiority, storage-fault durability, or an external replication result.
