## Confirmed corrections

### 1. Redis blocking reads override the general socket read timeout

In go-redis v9.7.0, [`XReadGroup`, lines 245-261](https://github.com/redis/go-redis/blob/ed37c33a9037483ad2a6b1042e5eb6df89009a1c/stream_commands.go#L245-L261) installs a command-specific read timeout whenever `Block >= 0`. [`cmdTimeout`, lines 470-478](https://github.com/redis/go-redis/blob/ed37c33a9037483ad2a6b1042e5eb6df89009a1c/redis.go#L470-L478) returns **Block + 10 seconds** for a positive block duration, rather than `Options.ReadTimeout`. [`WithReader` and `deadline`](https://github.com/redis/go-redis/blob/ed37c33a9037483ad2a6b1042e5eb6df89009a1c/internal/pool/conn.go#L66-L127) apply this timeout when entering the socket-read phase. A zero block duration is a separate infinite-read case, not a ten-second deadline. Context deadlines are not enabled by this harness; the library's [context selection](https://github.com/redis/go-redis/blob/ed37c33a9037483ad2a6b1042e5eb6df89009a1c/redis.go#L633-L638) confirms that distinction.

| Actual harness call | Redis server `BLOCK` | Effective positive socket-read timeout |
|---|---:|---:|
| Drain workers and new-read-only controls, `bench/main.go:319,564` | 100 ms | 10.1 s |
| Initial victim receive, `bench/main.go:497` | 5 s | 15 s |

The server normally returns an empty blocking read near its configured blocking interval. The longer client deadline is a transport safeguard, not the normal wait or reclamation timer. `XAUTOCLAIM` and `XACK` do not install this override. Redis's general settings are separate read/write socket timeouts, not an absolute five-second bound on an entire API call. NATS `AckSync(AckWait(5s))` uses a request-response wait.

**Suggested methods clarification:** “Redis uses five-second default socket read and write timeouts, except that go-redis assigns positive blocking `XREADGROUP` calls a read timeout equal to `BLOCK` plus ten seconds. Drain and control reads use `BLOCK=100 ms`; the victim's initial read uses `BLOCK=5 s`. These socket limits are distinct from server blocking intervals and consumer acknowledgment deadlines.” Add a citation for the pinned `redis.go` path; the existing `goredis970` entry only names `stream_commands.go` and does not alone show the ten-second addition. Qualify the word “budgets” at `paper/main.tex:273` accordingly.

## Central implementation claims remain supported

- **Redis recovery:** new-message reads do not automatically reclaim a failed consumer's pending entries. `XAUTOCLAIM` scans at most `10 * COUNT` entries, skips idle age strictly below the threshold, and updates ownership and delivery time after a claim. Equality is eligible in the pinned implementation. Cursor advancement and later revisits remain application responsibilities. [`t_stream.c:3355-3503`](https://github.com/redis/redis/blob/a0a6f23d997b024689ba157916837f493a593a34/src/t_stream.c#L3355-L3503), [official command documentation](https://redis.io/docs/latest/commands/xautoclaim/). The single-pending-message model is appropriately narrower than large-PEL recovery.
- **Redis AOF:** always mode performs synchronization and exits on an fsync error; everysec can postpone writes while background fsync is busy. The source does not establish a universal one-second loss bound. [`aof.c:1082-1104`](https://github.com/redis/redis/blob/a0a6f23d997b024689ba157916837f493a593a34/src/aof.c#L1082-L1104), [`aof.c:1222-1253`](https://github.com/redis/redis/blob/a0a6f23d997b024689ba157916837f493a593a34/src/aof.c#L1222-L1253). The server explicitly flushes AOF before pending client replies in the relevant path: [`server.c:1733-1757`](https://github.com/redis/redis/blob/a0a6f23d997b024689ba157916837f493a593a34/src/server.c#L1733-L1757). Group-state propagation is supported by [`t_stream.c:1542-1576`](https://github.com/redis/redis/blob/a0a6f23d997b024689ba157916837f493a593a34/src/t_stream.c#L1542-L1576). Group commit wording is consistent with [official persistence documentation](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).
- **JetStream expiry and client demand:** the pinned server compares pending age with `AckWait`, queues expired entries, and adds the nominal one-millisecond timer delay. [`consumer.go:2477-2487`](https://github.com/nats-io/nats-server/blob/1d6f7eaf0bd966dd02c95b8d5f624868f1a62544/server/consumer.go#L2477-L2487), [`consumer.go:4608-4723`](https://github.com/nats-io/nats-server/blob/1d6f7eaf0bd966dd02c95b8d5f624868f1a62544/server/consumer.go#L4608-L4723). nats.go v1.39.1 `Fetch(1)` avoids the initial no-wait probe and shortens server request expiry by 10% of remaining client time, capped at five seconds. Empty timeout responses can leave the described demand gap. [`js.go:2986-3065`](https://github.com/nats-io/nats.go/blob/4ba1afe8709b048ae89888f0f94da7eb8497e7ec/js.go#L2986-L3065). The manuscript's “approximately” and “possible” qualifications are necessary.
- **JetStream append versus consumer progress:** stream creation sets `AsyncFlush=false`, and the store flushes in place before the publication response. [`stream.go:616-631`](https://github.com/nats-io/nats-server/blob/1d6f7eaf0bd966dd02c95b8d5f624868f1a62544/server/stream.go#L616-L631), [`stream.go:4615-4715`](https://github.com/nats-io/nats-server/blob/1d6f7eaf0bd966dd02c95b8d5f624868f1a62544/server/stream.go#L4615-L4715). ## Final mathematical and Lean mapping audit

Read-only inspection on 2026-09-24 covered every displayed model statement and hand proof in `paper/main.tex`, the related result interpretations, all declarations in `formal/DeliveryModel.lean`, its README, and the retained verification log. No Lean, analysis, benchmark, or hash computation was executed. **No critical algebraic or logical defect was found.** The following narrow clarifications would make the quantifiers and statistical scope more explicit; line numbers refer to the inspected manuscript.

1. **Per-run occupancy identity, `main.tex:153-157`.** Introduce the ratio equation with “For two individual trials with positive mean cycle times, this gives the exact decomposition.” Positivity excludes zero denominators, which the basic nonnegative-interval definition otherwise permits. Add “This identity does not generally survive separately averaging throughput, occupancy, and cycle time across trials.” The reported ratio of condition-mean throughputs is a different summary. The existing results correctly avoid substituting a p99 for mean cycle time and do not identify a particular contention mechanism from this algebra.
2. **Bootstrap assumption, `main.tex:265`.** Ordinary resampling of block vectors treats the sampled completed blocks as independent, identically distributed replicates. Exchangeability alone permits dependence and is not sufficient justification. Replace that phrase with “under the working resampling assumption that completed block vectors are independent, identically distributed replicates.” Retain the existing warnings about serial dependence, the shared testbed, small samples, and conditioning on completion. No finite-sample bootstrap coverage theorem is provided or needed for the stated nominal, qualified intervals.
3. **Unbounded-delay alternative, `main.tex:106,113`.** For logical precision, say “If the corresponding upper-bound premise is removed and admissible selection or observation delays are unbounded, no finite uniform recovery bound follows.” The finite-bound theorem itself assumes finite `P` and `B`; an unknown bound is not the same proposition as an unbounded admissible delay. The existing construction is valid for the latter alternative.
4. **Parameter domains and service window.** Explicitly state `n >= 1` and `0 < alpha < 1` in the binomial-limit derivation, and `N >= 1`, `0 < p <= 1` for nearest-rank percentiles. These hold for the reported uses. For the synchronization-service paragraph (`main.tex:172`), specify an interval containing all `F` complete, nonoverlapping synchronization operations. The `b/f_min` bound then follows from count at most `bF` and elapsed time at least `F f_min`; it is not a bound for an arbitrary observation window cutting through operations.
